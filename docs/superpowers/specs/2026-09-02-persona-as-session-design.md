# W6 설계 — 페르소나를 세션 정체성으로

- **작성일**: 2026-09-02
- **상태**: 검토 대기
- **상위 문서**: `docs/superpowers/specs/2026-08-31-secu-agent-design.md`
- **정정 대상**: `docs/superpowers/specs/2026-09-01-w3-deployment-design.md` §3.2 (고지의 위치)

---

## 1. 문제

배포된 화면을 처음 보는 사람은 **이것이 누구의 화면인지 알 수 없다.**

지금 페르소나는 `/ask` 페이지의 로컬 React 상태다. 다른 화면과 공유되지
않고, 새로고침하면 사라지며, 나머지 화면(`문서·권한`·`계정`·`감사 로그`)은
전부 장치를 위에서 내려다보는 메타 화면이다. 그래서 사이트 전체가 **직원이
쓰는 서비스가 아니라 시연 장치의 조작판**으로 읽힌다.

이 프로젝트가 증명하려는 것은 "같은 질문에 사람마다 다른 답이 온다"인데,
그것을 보여주는 화면이 정작 "그 사람"이 되어보는 경험을 주지 않는다.

## 2. 결정

### 2.1 화면을 네 면으로 나눈다

```
구글 로그인
   ↓
허브 /
   ├─ 세 직원 카드 ─────────────→ 직원 면
   └─ "어떻게 동작하는가" 입구 ──→ 설명 면

직원 면          쿠키에 페르소나 이름
   ├─ 질의
   └─ 내 문서                     나가기 → 허브

설명 면          페르소나 불필요. 로그인한 누구나
   ├─ 동작 원리
   ├─ 계정
   └─ 문서 가시성 표

관리자 면        role === "admin". 서버가 다시 확인
   ├─ 감사 로그
   └─ 관리자 대시보드
```

**허브가 홈이다.** 직원 면에서 나가면 항상 여기로 온다. 설명 면 입구도
여기 있다 — 직원 화면 안에 "직원이 볼 리 없는 메뉴"를 섞지 않기 위해서다.

### 2.2 페르소나는 서버 쿠키에 **이름만** 담는다

앱 셸(`app/(app)/layout.tsx`)이 이미 서버 컴포넌트다. 쿠키를 읽어 헤더와
네비를 그 사람의 것으로 렌더하고, "내 문서"를 서버에서 그대로 그린다.
새로고침과 직접 URL 접근에 견딘다.

**기존 불변식을 깨지 않는다.** `api/schemas.py` 가 적어둔 규칙 —

> AskRequest 에 department·clearance 가 **없다**. 클라이언트가 그것을 보낼
> 수 있으면 그 값이 곧 사칭 경로다. 페르소나 이름만 받고 서버가 principals
> 테이블에서 번역한다.

— 은 쿠키에도 그대로 적용된다. 쿠키에 담기는 것은 **이름뿐**이고 등급·부서는
여전히 백엔드가 `principals` 테이블에서 번역한다. 쿠키를 조작해도 얻을 수
있는 것은 "다른 페르소나 되기"이고, 그것은 애초에 허브에서 클릭 한 번으로
되는 일이다. 새로 열리는 문이 없다.

쿠키가 없는 채로 직원 면에 접근하면 허브로 보낸다. 세션이 없으면 `/` 로
보내는 기존 패턴과 같은 모양이다.

**대안을 버린 이유.** URL 경로(`/as/kimdev/ask`)는 링크 공유가 되지만 한글
이름의 영문 슬러그 매핑이라는 새 개념이 생기고 모든 링크에 페르소나가
따라붙는다. 클라이언트 상태 유지는 가장 적게 고치지만 서버가 페르소나를
몰라 헤더에 이름을 띄울 수 없다 — 이 작업이 하려는 일의 핵심이 안 된다.

### 2.3 시연 고지는 헤더가 집이다 (W3 §3.2 정정)

W3 스펙 §3.2 는 고지를 **"UI 의 페르소나 선택기 옆"** 에 두라고 지정했다.
선택기가 사라지므로 그 지시는 갈 곳을 잃는다.

**정정: 직원 면 헤더가 고지의 집이다.**

```
김개발 · 개발팀 · 등급 1 — 시연용 계정 ⓘ
```

`ⓘ` 를 누르면 펼쳐진다: 인증은 실제 구글 OAuth이고, 부서·등급은 시연을 위해
선택하는 값이며, 선택된 값이 실제 권한 필터를 그대로 탄다.

W3 §3.2 의 **원칙**("감추면 그것이 거짓 주장이 된다")은 그대로다. 바뀌는
것은 위치뿐이다. 상시 노출이되 작게 두어, 직원 화면의 몰입을 깨지 않으면서
거짓 주장도 하지 않는다.

### 2.4 감사 로그는 관리자 전용이고, **권한 없는 조회 경로를 만들지 않는다**

`감사 로그` 화면은 지금 껍데기이고 거짓을 말한다 — *"log_events 스키마는
이미 있고 적재는 W4 에서 채웁니다"* 라고 적혀 있으나 W4a 가 적재를 끝냈고
DB 에 33건이 있다. `adminOnly: false` 라 낯선 방문자가 그 낡은 화면을 본다.

이번에 **실제로 만든다.** 그런데 여기 이 프로젝트의 핵심 제약이 걸린다.
`core/ports.py` 의 `LogSearch.query()` 는 `Principal` 을 필수 인자로 받는다:

> principal 이 필수 인자인 이유는 ChunkSearch 와 같다 — **권한 없는 조회를
> 호출할 방법이 없다**(상위 spec 5.3).

즉 저장소에 권한 필터를 우회하는 로그 조회 경로가 **존재하지 않는다.**
관리자 편의를 위해 하나 만들면 그것이 바로 이 프로젝트가 테스트로 막아온
그 우회 경로다. `demo/naive_search.py` 를 격리하면서까지 지킨 규율을
관리자 화면이 뒷문으로 깨는 셈이 된다.

**결정: 감사 로그 화면도 주체의 눈으로 본다.** 화면 안에 주체 선택기를 두고,
고른 주체가 보는 이벤트만 나온다. 관리자 면에는 페르소나 쿠키가 없으므로
이 선택기는 화면 로컬 상태다 — 직원 면에서 선택기를 걷어낸 것과 모순되지
않는다. 직원 면은 *한 사람이 되어보는* 곳이고, 관리자 면은 *장치를
들여다보는* 곳이라 도구가 달라야 한다.

이 제약은 오히려 이 화면이 보여줄 수 있는 가장 좋은 것이다. 같은 로그
질의를 주체를 바꿔 던지면 **개수와 내용이 달라지고**, 그것이 문서에 걸린
것과 **같은 `visible()` 하나**로 판정된다는 사실이 화면에서 그대로 보인다.
`/how` 패널 ④ 가 말로 하는 주장을 여기서는 실행으로 보여준다.

### 2.5 문서 화면이 둘로 쪼개진다

지금 `문서·권한` 은 전체 문서 목록과 누가 무엇을 보는지의 표다. 두 성격이
한 화면에 섞여 있다.

- **직원 면 "내 문서"** — 내 등급·부서로 열람 가능한 문서만. 다른 직원으로
  다시 들어와 같은 화면을 보면 **목록 길이가 달라진다.** 그 자체가 증명이다.
- **설명 면 "문서 가시성 표"** — 지금의 메타 뷰. 전체 문서 × 세 주체의 격자.

### 2.6 나가는 문이 둘이다

| 동작 | 위치 | 결과 |
|---|---|---|
| **나가기** | 직원 면 헤더 | 페르소나 쿠키만 지운다 → 허브. 구글 세션은 유지 |
| **로그아웃** | 허브 헤더 | 구글 세션을 끊는다 → 로그인 화면. 쿠키도 함께 지운다 |

직원 면에 구글 로그아웃을 두지 않는다. "다른 직원으로 보고 싶다"는 요구에
구글 재로그인을 시키면 시연이 끊긴다. 반대로 허브에 "나가기"를 두지 않는다 —
이미 나온 상태다.

## 3. 화면별 변경

| 경로 | 지금 | 바뀐 뒤 | 면 |
|---|---|---|---|
| `/` | 로그인 화면 | 미로그인이면 로그인 화면, 로그인했으면 **허브** | — |
| `/ask` | 페르소나 선택기 + 질의 | 질의만. 정체성은 헤더가 | 직원 |
| `/my/documents` (신규) | — | **내가 볼 수 있는 문서** | 직원 |
| `/documents` | 전체 문서 + 권한 표 | **문서 가시성 표**만 남는다 | 설명 |
| `/principals` | 계정 목록 | 그대로 | 설명 |
| `/how` | 동작 원리 | 그대로 | 설명 |
| `/logs` | 낡은 껍데기, 누구나 | **log_events 뷰어, 관리자 전용** | 관리자 |
| `/admin` | 관리자 대시보드 | 그대로 | 관리자 |

`/` 는 지금도 미로그인 사용자에게 로그인 화면을 보여준다. 바뀌는 것은
**로그인한 사용자가 `/` 에 왔을 때**다 — 지금은 그대로 로그인 화면이 보이고,
바뀐 뒤에는 허브가 보인다.

## 4. 백엔드 변경

`log_events` 조회용 HTTP 엔드포인트가 없다. 하나 더한다.

```
GET /log-events?persona=&event_type=&since=&limit=
```

- `persona` 이름을 받아 서버가 `principals` 에서 `Principal` 로 번역한다 —
  `/ask` 와 같은 방식이고 같은 이유다.
- 기존 `PgLogSearch.query()` 를 그대로 쓴다. **새 SQL 을 쓰지 않는다.**
- 시크릿 검사 뒤에 둔다. 관리자 판정은 BFF 가 한다(`/api/access-log` 와 같은
  모양).

## 5. 테스트

**백엔드** — 새 엔드포인트는 기존 패턴을 따른다: 시크릿 없으면 401, 알 수 없는
페르소나면 400, 주체에 따라 개수가 갈리는 것을 db 테스트로 못 박는다. 후자가
핵심이다 — 갈리지 않으면 이 화면이 보여줄 것이 없다.

**프론트엔드** — 지금 `npm test` 는 `lib/*.test.ts` 만 돈다. 컴포넌트에 자동
검증이 하나도 없다. 이 작업은 **서버 쪽 로직**(쿠키 읽기, 페르소나 해석,
면별 접근 판정)을 `lib/` 의 순수 함수로 빼서 그 자리에서 테스트한다.
컴포넌트 테스트 도구를 새로 들이는 것은 이 범위 밖이지만, **판정 로직이
컴포넌트 안에 숨지 않게** 하는 것은 이 범위 안이다.

특히 다음 셋은 순수 함수로 두고 테스트한다:
- 쿠키의 페르소나 이름 → 유효/무효 판정
- 면별 접근 판정(직원 면에 쿠키 없음 → 허브, 관리자 면에 member → 되돌림)
- 네비 구성(면 × role → 보이는 항목)

## 6. 반응형 — 좁게만 포함

앱 셸이 `236px 1fr` 고정이고 페르소나 그리드가 고정 3열이라 모바일에서
깨진다. 전면 반응형은 이 범위 밖이다(별도 작업).

**단 허브는 포함한다.** 허브가 방문자가 처음 닿는 화면이고, 링크를 폰으로
여는 사람이 첫 화면에서 깨진 레이아웃을 보면 나머지를 보지 않는다. 허브의
직원 카드가 좁은 화면에서 세로로 쌓이게 하는 것까지가 이번 범위다.

## 7. 완료 조건

- [ ] 로그인 직후 허브가 뜨고, 세 직원 카드와 설명 입구가 보인다
- [ ] 직원을 고르면 그 사람의 헤더가 붙은 직원 면으로 들어간다
- [ ] 새로고침해도 그 직원이 유지된다
- [ ] "나가기"를 누르면 허브로 돌아와 다시 고를 수 있다
- [ ] 직원 면에 페르소나 선택기가 없다
- [ ] "내 문서" 목록 길이가 직원에 따라 달라진다
- [ ] 헤더의 시연 고지가 상시 보이고 펼치면 설명이 나온다
- [ ] 쿠키 없이 직원 면 URL 로 직접 들어가면 허브로 보내진다
- [ ] `member` 로 `/logs`·`/admin` URL 에 직접 들어가면 되돌려진다
- [ ] 감사 로그가 실제 `log_events` 를 보여주고, 주체를 바꾸면 결과가 갈린다
- [ ] **권한 필터를 우회하는 로그 조회 경로가 저장소에 없다**
- [ ] 허브가 좁은 화면에서 깨지지 않는다
- [ ] 낡은 "적재는 W4 에서 채웁니다" 문장이 저장소에서 사라졌다

## 8. 범위 밖

- **전면 반응형** — 허브를 뺀 나머지 화면. 별도 작업.
- **컴포넌트 테스트 도구 도입** — 판정 로직을 `lib/` 로 빼는 것까지만 한다.
- **`draft_report`·`verify_clauses`** — 상위 spec §7. 기능 확장이라 별개다.
- **관리자가 아닌 방문자에게 감사 로그를 열어주는 일** — 이번 결정으로 닫혔다.
